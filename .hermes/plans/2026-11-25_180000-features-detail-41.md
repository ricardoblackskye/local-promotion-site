# #41 — SkyeForge Features: cards open a detail page

Plan for `ricardoblackskye/local-promotion-site#41`. Gate 1 pending: no implementation code until this
is approved.

## Goal

Clicking a card in the Services & Expertise collection opens a detail page about that entry. The
section is renamed **SkyeForge Features**, and the route is `/features`.

The collection is Wix's `Services`. `title` and `description` are already fetched; the **missing
fields are `Details` and `Image`**.

## The one ambiguity, and how I will resolve it

The issue says *"The path should be /features"* and also asks for a **detail page** per card. A single
path cannot be both, so I read it as:

| route | what it is |
| --- | --- |
| `/features` | the renamed collection page (today the home-page section) |
| `/features/:slug` | the detail page for one entry, keyed on the `slug` already fetched |

That mirrors `/blog/:slug`, which this repo already does. **If you meant `/features/<something else>`
— an id, or a different shape — say so and the plan changes in one line rather than in the code.**

## Added on review: a way back to the home page

Requested: a method to navigate back to the home page at the top, e.g. a breadcrumb menu.

### The finding that shapes it

`src/components/layout/Header.tsx` does not navigate by ROUTE - it navigates by SCROLLING to a
section id on the home page:

```ts
function scrollToSection(sectionId: string) {
  const el = document.getElementById(sectionId)
  if (el) el.scrollIntoView({ behavior: "smooth" })
}
```

On `/features/:slug` there is no such element, so every header nav click silently does nothing,
and the logo (which calls `scrollToSection("hero")`) is likewise a dead control. A new route
therefore does not merely lack a way home - it inherits a header whose controls appear live and
are inert. That is worse than no header, because a click that does nothing reads as a broken page.

### The requirement, as it becomes a task

| # | Task | The RED asserts |
| --- | --- | --- |
| 7 | A breadcrumb at the top of the detail page: `Home / SkyeForge Features / <entry title>` | the `Home` segment is a link to `/`, the middle one to `/features`, and the current entry is not a link |
| 8 | The header is route-aware: off the home page its controls navigate rather than scroll | clicking the logo from `/features/:slug` goes to `/`; on `/` it still scrolls to the hero |

Task 7 is the request. Task 8 is the reason the request needs to be more than a breadcrumb: a
breadcrumb gives one route home, while the header above it is showing controls that no longer work.

### Shape, and what it deliberately excludes

- The breadcrumb is a small component, so the blog detail page can adopt it later; **it is not
  retro-fitted here**, to keep this change to the surfaces the issue names.
- The header keeps its scroll behavior ON the home page. Changing it everywhere would alter the
  home page, which the issue does not ask for.
- Where the Header and Footer render is a real design question: today they sit inside the home page
  component rather than the app shell, so a new route must render them itself or the shell must own
  them. The plan takes the second, smaller-risk option: the shell owns the layout, so every route
  gets a header rather than each page remembering to add one.

Both tasks are RED-first like the rest, and both carry the control that matters: on the HOME page,
nothing about the existing navigation may change.

## Amendments made while implementing (recorded, not implied)

### Task 8 grew: four inert controls, not two

The plan named the nav and the logo. Reading the header showed the same defect in four places: the
desktop nav, the mobile nav, the logo, **and "Hire Me"** - all call `scrollToSection`, so all of them
are inert off the home page. The nav and the logo are pinned by tests; "Hire Me" is fixed for the same
reason, since the defect is identical and leaving one control lying would be fixing the symptom in one
place and not the other.

Both navs now share one `NavControl`, which also keeps keyboard activation where it was - the existing
Enter/Space tests would otherwise have caught a silent loss of keyboard support.

### `Details` renders as paragraphs, not through `ricosRenderer`

The plan said the long-form copy would go through the Ricos renderer. It renders as split paragraphs
instead, because **no real value was ever in hand** to shape a rich-content document against, and a
renderer written without seeing one is a guess dressed as a feature. The page comment says so. When a
real `Details` value is available, swapping the renderer is a one-line change.

### The per-slug hook is built on the collection hook

`useWixService(slug)` reads the collection through `useWixServices`, which the cards already use, so a
detail view shares that cache rather than issuing a parallel request. The collection is small, so
finding the slug in the result is honest rather than clever. The plan implied a second query.

### The prender risk is resolved: this repo does not prerender

The plan flagged that a new route might need registering on a prerender path. Verified: there is no
`entry-server` file, no `prerender` or `ssg` step in `package.json` or `vite.config.ts`, and
`dist/index.html` is a 2.2 kB shell with a single `id="root"` that the client fills. It is a plain SPA,
so no extra registration is needed - and the claim came from a Dark Factory plan that cited
`src/entry-server.jsx`, a file that does not exist. That is a finding about the factory, filed
separately rather than folded in here.
