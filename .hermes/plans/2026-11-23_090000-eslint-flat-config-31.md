# Plan - ESLint v10: one config both gates can read (#31)

**Issue:** #31 | **Parent:** #20 | **Branch:** `fix/31-eslint-v10` | **Status:** in progress

## Goal

MegaLinter's ESLint and the repo's must **read the same config**, so they stop checking different
things. Four descriptors cannot run at all today - `JAVASCRIPT_ES`, `JSX_ESLINT`, `TSX_ESLINT`,
`TYPESCRIPT_ES` - because MegaLinter's ESLint 10 refuses the legacy `.eslintrc.cjs` that #17 added
deliberately to fit the repo's pinned 8.57. Neither choice is wrong; they are incompatible.

## What the original plan got wrong

**Option B (one config, both majors) is closed** - that much held up: eslint 8.57 + a flat config
crashes on brace expansion, and eslint 10 + that config crashed on `react-hooks@4.6` calling
`context.getSourceCode()`.

**But the diagnosis of the first crash was wrong, twice.**

1. Not the **eslint major**: eslint 10 crashed the same way on its own `@eslint/config-array`.
2. Not **which** brace-expansion version: repinning 2.1.7 changed nothing.

The cause was a **cross-major override**. The advisory-driven overrides in `package.json` forced
versions across majors into consumers written against another:

```
overridden minimatch@"^11.0.1"     (was "^3.1.2") from @eslint/eslintrc@2.1.4
overridden brace-expansion@"^2.1.7" (was "^5.0.0") from minimatch@11.0.9
```

Both surface as `brace_expansion_1.expand is not a function` at glob brace-expansion time, so the
failure presents as a *config* problem and is not. **Removing the `brace-expansion` override fixed
what two eslint majors could not**: minimatch 11 then resolves `brace-expansion@5.1.0` for itself.

Consequence: **the original Step 1 ("fix the interop first") dissolved.** It was never a separate
prerequisite - it was a one-line correction to the overrides.

## Where this actually stands

- eslint **10.15** installed with post-v9-API plugins; `eslint.config.js` written mirroring
  `.eslintrc.cjs` (including #17's deliberate `__mocks__` ignore); `--print-config` resolves
- **Rule parity: 91 -> 103, with 8 rules LOST** - `no-extra-semi`, `no-inner-declarations`,
  `no-mixed-spaces-and-tabs`, `no-new-symbol`, `no-var`, `prefer-const`, `prefer-rest-params`,
  `prefer-spread`. All eight were **removed from `eslint:recommended` in ESLint 9/10**, so extending
  the new recommended set drops them. `prefer-const` is a real signal, not a style opinion.
- **`npm run lint` reports 50 errors, 47 of them `no-undef`** (37 in `scripts/`). That is the
  config being **broader than the gate it replaces**: `js.configs.recommended` applies to all files
  while the node/browser globals apply only to `**/*.{ts,tsx}` - and the old gate only ever linted
  `.ts`/`.tsx` (its script was `eslint . --ext ts,tsx`).
- **Control passes**: a deliberate `no-explicit-any` fails, so nothing is disarmed.

## Remaining steps

1. **Re-add the 8 lost rules explicitly**, so the migration is not a quiet relaxation. Attach the
   `--print-config` set diff as evidence.
2. **Scope `js.configs.recommended` and the globals to the file set the old gate linted** - the
   migration must not widen scope any more than it must not narrow strictness.
3. `npm run lint` exits 0, with any residual `src/` findings examined on their merits (vitest
   globals are the likely cause of the rest).
4. `--ext` -> `files:` globs in the script, keeping `--max-warnings 0`.
5. **Control under both gates**: a deliberate break must fail the repo's lint *and* MegaLinter's.
6. **The notice must stop being emitted.** It is not decoration: it reports four descriptors as
   inert, and a check that cannot run is a failure, not an absence of failure.

## Acceptance

- `npm run lint` exits 0 and is **no less strict** than before - the 91 -> 103 set diff attached,
  with the 8 lost rules restored
- **all four** descriptors run through `eslint.config.js`, and **the notice is gone**
- the control fails under **both** gates
- no descriptor disabled, no rule silently dropped
